# 能力原语与状态空间搜索

**适用时机**：扫描器与逐类测试只产出零散低危（信息泄露/弱配置/越权读），没有任何单点高危——**这不是终点，是凑链的起点**。本剧本把每个已确证事实抽象为「能力原语」，用状态空间搜索把原语组装成高影响链（RCE / 认证接管 / 核心数据读取）。

## 一、能力原语表（每条确证发现 → 标注原语）

| 原语 | 含义 | 典型来源（低危发现即原语） |
|---|---|---|
| **READ** | 任意/受限文件或源码读取 | .git/.svn/备份泄露、sourcemap、路径穿越、XXE、api-doc 泄露 |
| **WRITE** | 任意/受限路径写（含上传落盘） | 上传点、头像/导入功能、日志写、临时目录可写 |
| **EXEC** | 命令/代码执行（最终目标） | 命令注入、SSTI、反序列化、模板渲染、脚本引擎 |
| **SSRF** | 服务端发起请求（内网可达性） | 盲/回显 SSRF、URL 预览、webhook、导入远程资源 |
| **SQLI** | 数据库读写（看权限边界） | 注入点 + information_schema + FILE 权限实测 |
| **AUTHZ** | 越权（水平/垂直） | IDOR、JWT 缺陷、会话混淆、admin 接口可达 |
| **CRED** | 凭据获取 | 源码硬编码、配置泄露、默认口令、历史泄露、弱口令实测 |
| **REDIR** | 开放重定向 / URL 可控跳转 | redirect 参数、SSO 回跳 |
| **PROXY** | 出网通道（回连/下载可控） | OOB 回连可达、出网 DNS/HTTP 可控 |

**登记纪律**：每条确证发现入库时，在 detail 末尾追加 `primitive:XXX`；同原语多来源取最强（受限 < 半受限 < 任意）。

## 二、RCE 六等式（凑链目标分解）

1. **WRITE + 路径可达** = webshell/计划任务/SSH key → EXEC（确认落点可解析或被加载）
2. **EXEC 原语直得**：SSTI/反序列化 gadget/命令注入/脚本引擎（javamelody、Groovy 控制台、模板后台）
3. **SSRF → 新攻击面** = 内网服务指纹 →（递归套用本剧本）→ 内网弱面 EXEC/新 CRED
4. **CRED + AUTHZ** = 后台登录 → 后台高危功能（模板编辑/插件上传/备份恢复/计划任务）→ EXEC
5. **SQLI(Secure_File_Priv 开放) → INTO OUTFILE / 日志写 → WEB 目录** = WRITE → EXEC
6. **READ → 配置 → CRED**（DB/Redis/OSS/SMTP/SVN）→ 登录或直连 → 五中取一 → EXEC

**反向搜索**：先声明目标（RCE / 核心数据），列出所需原语集合，逐环回推「现在手里有什么、缺什么、去哪个面找」——缺口就是下一轮测试计划（plan_subtasks 建项）。

## 三、低危 → 原语速查（发现后必问的三句话）

- sourcemap/源码泄露（READ）：源码里有没有 AK/SK、内网域名、加密密钥、隐藏接口？（grep key/secret/token/internal）
- SSRF（SSRF）：能不能打元数据（169.254.169.254）、内网指纹（常见端口/服务特征）、云函数/K8s API？
- 越权读（AUTHZ+READ）：能不能读到**别人的**会话/附件/导出文件 → 拿到更高身份？
- api-doc（READ）：文档里隐藏的管理接口/调试接口有没有独立认证缺陷？
- 备份/.git（READ）：历史版本里有没有已删除但仍有效的凭据/密钥？
- 弱口令实测成功（CRED+AUTHZ）：登录后**第一个动作是枚举后台高危功能**（见第四节）。

## 四、后台/立足点到手后的高危功能清单（EXEC 跳板优先级）

模板/主题编辑（Freemarker/Velocity/Jinja2）、插件/扩展安装上传、计划任务/定时器、备份恢复与还原、数据库管理/SQL 控制台、文件管理器、日志配置（log4j jndi/路径可控）、脚本控制台（Groovy/Jython/Beanshell）、反序列化导入（XML/Excel 宏/序列化会话）、容器/K8s 面板集成。

## 五、执行纪律（与本引擎护栏对接）

1. **每凑一环都有证据**：原语有效性以实测为准（差异证据/OOB 回连/受控文件落点确认），「理论可利用」不算链路成立。
2. **覆盖度记账**：链上每个候选环 update_coverage 登记（vulnerable / ruled_out 附证据），防止链路重复试错与报告漏项。
3. **利用动作转 S5**：本剧本在 S4 用于**发现与定性**；实际投递载荷/拿 shell 的动作按 S5 降级链执行并走审批（L2）。
4. **ROE 优先**：凑链过程中任何越界目标（范围外内网资产）只登记线索交人工确认；破坏性等式（DROP/覆盖原文件）禁止采用。
5. **诚实降级**：等式确实凑不齐时，报告按「最高达成权限层级」如实定级，把缺口写入《安全向量/盲区》——不虚报、不脑补。

## BURN 原语（付费能力滥用）

- **BURN**：厂商按次计费能力滥用——实名二要素验证、短信发送、活体检测、OCR 识别等"后端调付费第三方 API 且无频控"的接口
- 判据：前端校验通过但后端仍逐次调用付费 API（错误响应逐次返回）+ **响应长度差异可区分对错**
- 利用（v5.1 授权与频控硬门）：对身份证后 4 位 0000-9999 爆破（长度差判对错）→ 既是漏洞（无限资源消耗=厂商成本）也是社工信息放大器。**频控：单接口 ≤20 次/窗口（抽样差分足够判"无频控+长度 oracle"，禁止跑满万次）；累计配额写进审批 reason；按次付费类动作 L1 起审批，命中即停**——万次级打生产计费 API 属 DoS 性质
- 同族点位枚举：二要素、短信、活体、OCR——全部按"前端拦截→后端直调"模式测
