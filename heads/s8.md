# 阶段 8 · 报告与修复建议（REPORTING）

**目标**：把技术发现转译成管理层可决策、工程师可修复的交付物。进入条件：全部证据已归档。

## 分步动作

1. **S8-1 漏洞定级（去重与反夸大硬规则）**：逐条读取记忆库发现，按 CVSS v3.1 评分 + 业务影响定级（P0-P4）；产出《漏洞定级表》。**必须遵守**：
   - **根因去重**：同一漏洞机制 + 同一修复动作的发现合并为一条报告条目，多种「表现/后果」写在同一条目内（例：JWT alg:none 的伪造身份、越权、提权 = 1 条，不是 3 条）。P0/P1/P2 计数 = **独立根因数**，不是发现条数；定级表必须附「原始发现 → 报告条目」合并映射。
   - **反过度推断**：数据结构中存在某字段 ≠ 可利用（反例：某令牌字段仅在用户主动发起重置流程时才写入、默认为空，则「可直接接管任意账号」的断言不成立）；利用前提（可触发、可达、有载荷落点）必须逐项实测，未实测的利用路径一律降为「待验证」并单独列出，**不计入 P0/P1 计数**。
   - **quality-pending 复核确认（v5.3.8）**：收口若提示「部分阶段带 quality-pending 复核标记」——逐个复核这些阶段的交付物与发现（无缺口即可），然后重新调用 complete_stage 并传 `"confirm_quality_review": true`；引擎清除标记并继续收口。不要尝试用 update_finding 或其他工具清除该标记（均不可达）。
   - **后渗透范围标注（v5.3.7）**：s6 阶段状态为 skipped 时，报告「测试范围」或对应章节显著标注「后渗透：创建时未勾选，未执行（用户范围决策）」——不算漏测，不得默默省略；勾选且已执行则按正常口径呈现。
   - **证据引用强制**：每条 P0/P1/P2 报告条目必须引用实测复现命令（EV-xxx / 证据文件路径）；只有推测的条目置信度标「待查」。
   - **P0 定义收紧**：P0 = 零门槛（无凭据/无用户交互）可直接造成严重影响的独立根因；需要多前提的组合链在条目内说明链路，不重复计数。
2. **S8-2 报告撰写**：用 write_file 生成 `report.md`，结构：
   - **执行摘要**（管理层视角：整体风险、关键数字、最需关注的三件事）
   - **测试范围与方法**（资产、时间线、审批矩阵执行情况）
   - **发现详情**（每条：编号/标题/等级/置信度/位置/**漏洞详细介绍**/复现步骤/**修复建议**——v5.3.6 起直接引用 finding 库 detail/poc/remediation 三字段（页面与报告同源， remediation 缺失时补写后同步 update_finding）；复现步骤必须用 **Burp 原文对照格式**：成对的「请求原文/响应原文」块（record_finding poc 参数或技能库 report-writing 标准），不允许只写文字描述）
   - **多目标分组交付物合并（v6.4.0，兑现 s4.md S4-9/s5 交付物节的承接约定；v6.6.0 SP-① 扩展三专项分组；v6.8.0 S7-④ 补 s6 分组——与 v6.7.0 S6-④ 分组产出约定对齐）**：开工先 read_file 全部 `deliverables/s4-<目标或组名>.md`、`deliverables/s5-<目标或组名>.md`、`deliverables/s6-<目标或组名>.md` 与 `deliverables/specA-|specB1-|specB2-<目标或组名>.md` 分组文件——报告章节按目标组织，逐组核对漏洞清单与待续项无遗漏合并进《发现详情》与《清单外发现与盲区》（专项组结论并入对应章节与附录「AI 专项结论 / 专项 B1/B2 素材包」）；任一分组文件的已验证漏洞未进报告即交付缺项。v6.9.0 S8-⑥：分组文件以上下文「分组交付物承接」块为准（存在才列，单目标项目无此块）——收口前逐行核对，反思门问句 d 按此抽查。
   - **S7 收口承接（v6.8.0 S7-④）**：上下文「S7 收口移交」块逐件标注 s7 交付物（《影响评估》《清理确认清单》《需人工清理清单》《完整攻击时间线》《待续清单处置》）的报告承接落点与收口清点统计（needs_follow_up 处置 N/M、open VT、未用 L2）——统计非满即「未清完」，报告如实呈现，禁止静默省略。
   - **修复建议清单（带优先级）**
   - **清单外发现与盲区**（存在 `【清单外】` 标注发现时单列统计：条目/来源推断/深挖复盘——自述面与已知 CVE 映射之外的发现即潜在 0day 面；同时列出覆盖矩阵 deferred/needs_follow_up 项即「安全向量/盲区」）
   - **附录**（完整攻击时间线（承接 S7《完整攻击时间线》）、《需人工清理清单》引用（四元组移交人工执行）、《待续清单处置》引用（复测建议承接 S7-4 三要素）、AI 专项结论、专项 B1/B2 素材包引用——v6.8.0 S7-④：移交人工与复测建议是报告交付面的一部分）
3. **S8-3 汇报与移交**：产出汇报要点（一页纸）与移交附件说明（PoC / 流量 / 截图位置与复现环境说明）。v6.9.0 S8-⑧：《汇报要点》为 report.md 固定章节（`## 汇报要点`，一页纸口径），《修复建议清单（带优先级）》为 report.md 固定章节（与技能库 report-writing 报告结构对齐）——均不要求独立文件；确需独立成件时写 deliverables/ 并在 complete_stage 列明。

## 撰写效率纪律（实测瓶颈：全量复读+逐字转录曾把本阶段拖到 60+ 轮）

- 上下文包已含各阶段一行摘要与覆盖矩阵——**先写框架，缺什么再 read_file 定向取**，禁止为"写全"逐个复读全部交付物；
- 报告正文**引用+摘要为主**（指向 deliverables/ 文件与 EV- 证据编号），漏洞详情只在 P0/P1 展开；
- 目标 ≤40 轮完稿；每写完一节就落盘一次（write_file 增量覆盖 report.md），不要攒到最后。

## 交付物

- 工作区 `report.md`（《渗透测试报告》——《修复建议清单（带优先级）》与《汇报要点》为其固定章节，v6.9.0 S8-⑧ 消歧，不要求独立文件）。complete_stage 时列出全部交付物。**多目标项目（v6.4.0 S4-⑨；v6.6.0 SP-① 扩展三专项；v6.8.0 S7-④ 补 s6 分组；v6.9.0 S8-⑥ 承接清单在场）**：报告章节按目标组织——`deliverables/s4-<目标或组名>.md`、`deliverables/s5-<目标或组名>.md`、`deliverables/s6-<目标或组名>.md` 与 `deliverables/specA-|specB1-|specB2-<目标或组名>.md` 分组交付物的漏洞清单与待续项逐组合并进报告（承接 s4.md S4-9、s5 交付物节、s6 分组产出约定与三专项分组产出约定；分组合并以上下文「分组交付物承接」块为准），任一分组已验证漏洞未进报告即交付缺项。

## 高效撰写纪律（迭代预算有限，实测曾因通读全部交付物而耗尽预算）

- **禁止逐个通读历史交付物**：上下文包已含每份文件的摘要，摘要即为事实来源；只精读与当前章节直接相关的 2-3 个文件（如定级时精读 s4 漏洞清单、s5 利用报告）。
- **报告分段写入**：单次 write_file 参数过长会被截断——先写骨架（执行摘要+目录），再按章逐次追加；每段 ≤3000 字。
- **定级/报告/建议清单一次成形**：不要反复重写同一文件，修改用精确的章节重写。

## 注意

- LLM 起草、安全工程师校对：报告中每条发现必须有证据支撑，无证据的推测标注「待查」并单独列出。
- 反思门会对本阶段做专项核查：①是否存在同根因拆多条抬高计数；②P0/P1 是否全部有实测证据引用；③是否存在未实测的「可直接/可接管」类断言。被拦截需修正后重提。
