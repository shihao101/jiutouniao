# 阶段 5 · 漏洞利用与渗透（EXPLOITATION）

**目标**：证明漏洞真实可利用，拿到「立足点」，全程留证。进入条件：待利用队列非空、高危审批通道就绪。

## 分步动作

1. **S5-1 目标选择与利用规划**：按队列优先级选择目标——**队列按 S4-7 标注的 impact-rank 升序消费（RCE 系 > 认证绕过 > SQLi 提数 > SSRF > 上传），无凭证项目优先消费 access=anonymous 的高危项**；规划**最小影响**的利用方式与回滚方案；产出《利用方案》（需人工批准后执行）。**队列只有零散低危时**：load_skill capability-primitive-search 按 RCE 六等式做凑链规划（READ/WRITE/EXEC/SQLI/SSRF/CRED/AUTHZ 原语组装，六等式详见该技能第二节），把「凑链缺环」作为利用目标，而不是直接宣告无可利用项。
   **v5.1.3 承接反蒸发（硬规则）**：承接 S4 `ready_but_unexecuted`/待利用队列做改写（合并/换编队/让位）时，**逐条三态映射——执行 / 合并进新编队（写明新编号）/ 显式移交（进待续清单）**，禁止静默丢弃任何条目；改写后计划必须与 S4 清单一一对应（S8 复核按此对账，实战实证 TH-23/24 高价值候选曾因改写静默蒸发）。**v6.4.0 移交项在场与机械对账**：上下文「S4 移交项」块逐条列出 S4 收口的 V3 两清单与 route=browser-auth 认证路线移交项——开工先逐条三态映射并留痕（执行=update_coverage/VT 引用条目原文，合并·移交=写进 S5 交付物映射表），引擎在 S5 收口按条目原文/VT 编号逐条对账承接留痕，缺留痕拦截收口。**v6.5.0 目标级映射（多目标项目）**：移交项带 @目标 标签，逐条映射按目标进行——A 目标的留痕不释放 B 目标的同类条目，引擎按目标分桶对账。
2. **S5-2 PoC 生成与本地验证**：用 write_file 生成载荷与 PoC（Python/Shell），先在本地/受控环境验证逻辑，再作用于真实目标。**利用/验证前置依赖登录态时，先 load_skill session-state-chain 按决策树路由（有凭据→登录链 jar 复用→带态测试→清理；无凭据→默认 deny 下禁止注册，按 v5.8.0 口径不主动询问）**——路由走完仍无身份时**不得直接移交**：先按 S5-2a 走完 browser-auth，再按 v5.4 增补过 load_skill observable-degradation 四通道评估，不可行项按四元组 needs_follow_up 移交（移交原因写明四通道逐项不可行）；premise_failed 仅保留给「前提本身不成立」的单元（如目标无该功能面），禁止未走链就放弃登录态测试项。**SQL 注入手工确证/疑似 ≥2 个端点时必须按 sqli-deep「自动化批量扩展」过 sqlmap 批量提取（统一四件套 banner/user/db/is-dba），禁止只深验 1-2 个**。
2a. **S5-2a 认证获取（browser-auth）**：**开工先消费上下文「S4 移交项」块中 route=browser-auth 的移交项——S4 已还原的前置知识（加密协议/签名机制/验证码结论/UA 指纹特征）直接复用，不重复明文探测**。登录面命中 JS/WASM 加密、动态挑战 token、验证码渲染、UA 指纹过滤任一特征，或明文构造连续 2 轮失败时，**停止明文构造**，load_skill browser-auth 走真实浏览器合规登录（`/opt/tools/browser-kit/`，凭据只走环境变量；验证码按 v7.6.0 B6 自动打码链处理（本地 OCR captcha-ocr → 读图兜底【条件级：需图像输入通道，不可用则跳过该级】→ 行为型滑块/点选走浏览器轨迹模拟），同会话「取码→识别→立即提交」，禁止两段式重跑取码——不再 request_user_input 人工读码；连续 3 次识别失败或风控升级信号（账号锁定/挑战升级）即停止尝试，按四元组移交）→ 抓取 cookies/storage/端点清单 → CLI 接管执行测试主体；协议逆向（wasm2wat）降级为可选深挖项，不再是登录前置。失败额度与 curl 尝试合并统计。**v5.1 身份政策**：无凭据时按 identity-bootstrapping——L1 注册面只评估不注册（ROE `identity.auto_register` 默认 deny），v5.8.0 口径（不主动向用户询问身份——有则用、无则默认无）无身份时**先 load_skill observable-degradation 四通道评估（必做前置，见 v5.4 增补），不可行才按四元组 needs_follow_up 移交**；**会话伪造合规边界：仅基于已确证伪造漏洞构造自有会话（L5/L6），禁止窃取/重放真实用户活跃会话**。
3. **S5-3 审批与受控执行**：**开工先对照上下文《审批工单状态》块逐单核对 S3-7 预请求工单——approved 项按批准范围投递并引用 AP 编号、pending 项催办或改序、expired/rejected 项重新发起或说明替代方案（兑现 s3.md S3-7「S5 开工确认关键审批已就绪或已拒」）**；写操作/RCE/横向等高危操作全部经审批矩阵批准后执行；全流量经代理并记录。3b. **落点管理**：拿到执行/写盘能力后按 load_skill webshell-memshell 做落点选择与登记（四元组：路径/指纹/建议清理命令/验证命令，写入《上传文件记录清单》）——**v6.7.0 载体规范：四元组登记写入 `deliverables/s5-上传文件记录清单.md`（独立文件首选）；确需并入《需人工清理清单》等文件时，该文件名或一级标题必须含「上传落点」字样（引擎按文件名 s5-前缀+上传/落点 与内容四元组特征双轨识别落点记录，无锚点=S6/S7 承接不到）**——**v4.8.1 口径：上传走渐进验证（先常规文件类型再可执行脚本，协议原文见 load_skill upload-bypass『渐进式上传验证协议』；可执行脚本步生产档被治理门拦截属预期，isolated_lab 按审批矩阵执行），全部驻留只记录移交、不执行删除/重启/还原**，需要多轮交互的服务（数据库客户端/监听器）用 shell_open 会话而非反复 run_command。
3a. **利用选型降级链**：msf/searchsploit 现成模块验证（先本机复现载荷逻辑）→ 公开 PoC 适配（逐行读懂再改，禁止盲跑）→ 自写 PoC（load_skill poc-template）。每级产物受控验证后才能打靶。**msf 未安装/不可用时降级：searchsploit 检索（load_skill cve-weaponization）→ 公开 PoC 适配 → 自写 PoC，不得因 msf 缺失跳过第一级**；工具缺失按 loop-core 工具守则（install_tool 自动安装或如实写入交付物）。
4. **S5-4 AI 控制面利用（AI 目标）**：提取系统提示、绕过安全策略、经提示注入驱动工具调用越权（详见专项 A 的 A3-A7）。
5. **S5-5 凭据获取与会话接管**：从漏洞、配置错误与泄露数据中获取凭据，验证横向复用面；**凭据只登记摘要，不存明文**——一律 record_loot（掩码+来源+verified 状态），凭据相关结论同步 upsert_fact，S6 横向优先消费战利品库。
6. **S5-6 记录与回环**：每次利用记录：时间/载荷/结果/截图；发现新攻击面（新端口/新服务/新接口/内网可达面/新组件指纹）则 loopback 回退阶段 4 补充分析——宁可回环一次，不留「看到了但没测」的尾巴。工作区存在 `checklist.json` 时：本轮对清单条目的利用/验证同样按 S4-8 口径在 update_coverage 引用条目文本或 C 编号（s5 收口时 G2 门同 s4 口径对账）。
7. **S5-7 失败反馈环（必做）**：利用失败按原因 update_coverage——waf_blocked（记录拦截特征，可 load_skill waf-fingerprint 调整载荷后重试一次）/ patched（回写 s4 排除）/ premise_failed（回写假设修正）；同一目标×载荷最多重试 2 次。

## Agent 执行循环

每轮：选目标 → 生成 PoC → 风险分级 → 审批 → 执行 → 观察 → 反思 → 更新计划。

## 红线

- 破坏性动作默认禁止；生产数据只做「存在性证明」（截屏/计数/哈希摘要）不下载不外传；AI 自主利用必须受审批矩阵约束，可随时一键熔断。

## v4.6 S5 增补（投递纪律 + 对抗分型）

- 队列消费：impact-rank 升序 × **就绪度优先**——有就绪脚本的项先投递（签名/SM4/WASM oracle 立即转 CLI 投递器，每次投递响应原文落盘并回填 claims）；
- 对抗类目标先判 behavior_class 并 load_skill 对应 playbook；限速目标按 rate-limit-playbook 窗口化执行（单窗口 ≤6-10 请求，窗口间完全静默）；
- 浏览器通道动作前做 channel-snapshot（K1 强制）；批量动作遵守 js-challenge-waf-playbook 行为预算器。
- **多目标批量投递（v6.5.0 S5-⑧）**：多目标项目的一切同构利用/验证动作（同一 PoC 跨目标投递、同一四件套批量提取、同一门控探针族）优先 run_batch（{{TARGET}} 模板 + targets 清单）——逐目标隔离、一次审批覆盖本批、单目标失败不拖死整批；零产出/killed 逐条 record_vt（C31 门对账）。

## v5.4 S5 增补（无账号观测降级轨 + 凭据复用矩阵）

- **无账号观测降级轨（必做前置）**：S5-2a 身份链走完仍无账号时（v5.8.0：不主动询问，用户主动提供即入库），认证后项**禁止直接 premise_failed 全量移交**——load_skill observable-degradation 逐项过四通道评估（时延侧信道/缓存行为差分/错误文案差分/自建数据回流），可行项就地三态登记，不可行项按四元组移交（移交原因必须写明四通道逐项不可行原因）；移交清单同步进 S8 盲区章素材。
- **凭据复用矩阵（获得任一凭据集时必做）**：战利品库凭据（泄露/确证/破解）对**同主机其他认证后端**做单发抽样复用验证（每面 ≤ROE 额度上限，禁爆破；load_skill weak-cred-bruteforce「凭据复用矩阵」节）；ID 派生候选仅在有明确派生证据（口令=标识号固定片段已确证类）时按规则生成，单发验证。

## v7.1.0 S5 增补（PAE：链路级提议替代逐命令审批等待）

- **链路计划提议（chain_plan）**：凑链场景（primitive-graph 缺口 ≥2 环）不再逐命令等待——propose(kind=chain_plan, steps=[每步命令 ≤6]) 一次提交整链，引擎逐步过执行档预检后批准；链内每步执行时治理九门仍逐条强制（预检≠放行），每步带 abort_condition 与无害判据。生产档只允许存在性证明链；isolated_lab 才可完整 PoC 链。
- **审批 engine 档认知**：本项目默认 engine 档——L1 自动批准；L2 提交时 reason 写明无害判据（无害回显/随机标记/canary/受控 OOB/计数/哈希）即被引擎自动放行，数据破坏/驻留类语义全档位硬拒。被拒后改存在性证明形态或拆只读步骤，**不存在人工审批屏障等待**。
- **链路产出回写**：链路提案执行结果（每环产出/断环位置）update_proposal 回写账本——断环位置即下一轮 chain_plan 的反向回推输入。
