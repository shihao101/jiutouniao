# 阶段 7 · 影响证明与收尾（IMPACT & CLEANUP）

**目标**：量化业务影响，受控收尾（登记移交——智能体不执行目标侧清理，单一规则），恢复验证。进入条件：后渗透记录完整。

**开工动作**：`load_skill cleanup-handover`（S7 收口四件套模板——《需人工清理清单》四元组表 / 《清理确认清单》两类动作 / 《影响评估》三段框架 / 《待续清单处置》三选一行格式），再按下方 S7-2 承接上下文「S6 移交项」块逐项对账。

## 分步动作

1. **S7-1 业务影响量化**：可触达数据规模、可执行的操作、合规后果（个保法/等保/行业监管）；产出《影响评估》。
2. **S7-2 受控清理（清理铁律，逐条硬约束）**：
   - **v5.1.3 用户政策：自建数据同样只登记不删除**——自建账号/文件/载荷/记录（以创建时登记的唯一标记定位：测试用户名、探针文件名、载荷指纹）逐项登记四元组并入《需人工清理清单》移交人工，**不执行删除/还原**；「清理确认清单」的执行侧改为登记完整性核对+只读复核两类动作。
   - **先 SELECT 后登记（v5.1.3）**：先只读 SELECT 列出受影响的确切行集写入《需人工清理清单》（供人工参考），不执行删除/修改；不符如实上报。
   - **存量数据绝对不动**：测试前已存在的行/文件/模板禁止 DELETE/UPDATE/覆盖。存量行被注入载荷时列入《需人工清理清单》移交（v5.3.0：不再有「就地中和」类 UPDATE——单一规则：智能体不执行任何目标侧写操作清理）。
   - **原文可还原**：修改配置/模板前先把原文存入 evidence/；无法还原原文必须如实声明并移交。
   - **无法安全清理 = 不清理**：影响范围不能精确限定时不出手，列入移交清单说明原因。
   - 产出《清理确认清单》——仅含登记完整性核对与只读复核两类动作（每项四元组：路径/指纹/建议清理命令/验证命令，建议命令供人工执行参考，智能体不执行）；与《需人工清理清单》逐项对账——**缺登记由反思门专项核查拦截（v6.8.0 问句 b），四元组残缺由引擎提示级核对在场（v6.7.0 S6-②）**；本阶段不得出现任何波及存量数据的破坏性语句（护栏会拦截，反思门会核查）。
   - **v4.8.1 驻留工件豁免执行（重要）**：智能体产生的全部后门/驻留工件（包含但不限于上传类：文件马/内存马/上传文件/计划任务/服务/SSH 公钥/新增账号/注册表项/WMI 订阅/启动项修改）**一律不执行删除/重启/还原**——S7 对其只做三件事：①核对《上传文件记录清单》与《持久化记录》四元组完整（缺登记即拦截）②逐项并入《需人工清理清单》（建议清理命令+验证命令供人工参考）③只读复核驻留位置仍在原处（未发生意外变化）。**v6.7.0：S6 移交项以上下文「S6 移交项」块为准——开工先逐项对账，块中列出的《权限矩阵》《横向路径图》《持久化登记行》《存量移交项》必须逐条出现在《清理确认清单》与《需人工清理清单》对账结果中（块只置顶在场，残缺四元组由引擎提示级核对）。v6.8.0 增补：①《上传文件记录清单》以上下文块「S5 上传落点」小节与 s5- 交付物为准——s6 未勾选（skipped）时该小节是唯一结构化入口，开工必须逐项核对四元组完整；②V3 两清单（s4/s5/三专项就绪未执行·已批未用）与 L2 工单以上下文「就绪移交清点」块与「审批工单状态」块为准逐单核对——S7 只清点不再发起新工单，清点三选一（update_vt 执行 / closed-roe 附理由 / deferred 移交三要素）。**~~清理确认清单的「执行侧」仅适用于自建业务数据行~~（v5.3.0 废止：与 v5.1.3「自建数据只登记不删除」政策冲突——现行单一规则：清理确认清单仅有登记完整性核对+只读复核两类动作，自建业务数据行同样登记移交，不执行 DELETE。）
3. **S7-3 恢复验证与时间线**：确认目标恢复正常、无残留；整理全程可复现证据链；产出《完整攻击时间线》`deliverables/s7-攻击时间线.md`（用 record_timeline 的事件 + 证据记录汇总）。
4. **S7-4 待续清单处置（必做，引擎 G3 门硬校验）**：汇总全项目覆盖矩阵中 status=needs_follow_up 的条目，产出《待续清单处置》`deliverables/s7-待续清单处置.md`——每项三选一：①本轮补测（补测后 update_coverage 更新状态）；②范围外（附理由）；③移交复测建议（条件/步骤/前置）。每项必须在文本中引用端点关键词留痕（引擎按端点归账，零引用条目会拦截收口）；本项目所有待续项处置完毕才允许收口。

## 红线

- 清理建议命令仅供人工执行（智能体不做目标侧清理——单一规则）；无法确认清理干净的项必须如实标注并上报人工。
- **禁止波及存量数据**：任何针对测试前已存在数据的 DELETE/UPDATE/覆盖都被禁止（护栏分级 L2，违反即违规留痕）；与 ROE「禁止破坏性写入」一致，登记移交≠破坏。
- 只读复核口径：用只读命令核对测试前基线（S1 记录的资产/数据规模）与移交清单的一致性，差异逐条说明并写入《需人工清理清单》。

## v4.6 S7 增补（终态标记 + 清单清点）

- .async 全部日志必须有 [JT-JOB-END] 终态标记（引擎强制拦截）；无标记=被截杀——其覆盖单元同步 needs_follow_up 并在待续清单注明「部分覆盖」；
- ready_but_unexecuted / l2_approved_unused 逐条三选一处置（补测完成 / 范围外附理由 / 移交复测含启动条件/步骤/工作量三要素）；
- 恢复验证后核对本阶段 update_finding 修订是否全部落库（结论修正不得只存在于增量报告）。

## 执行模式契约（v5.3.1，与 loop-core 规则 6 / policies/execution-profiles.yaml 对齐）

- **production_safe**（默认）：收尾一律**登记移交**——《需人工清理清单》四元组核对完整 + 只读复核，不执行任何目标侧删除/修改/还原（v5.3.0 单一规则不变，v5.3.1 起引擎在全部通道强制）；
- **isolated_lab**：自建工件经**快照恢复/环境重置**回收（恢复成功须只读验证），同样不在目标上执行清理命令——生产与实验室共用「智能体不执行删除」单一规则，回收方式按模式分流；
- 两种模式统一红线：禁止波及存量数据、禁止向公网分发测试产物（lab 档内也禁止）、S7-4 待续清单三选一处置不变。
