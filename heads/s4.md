# 阶段 4 · 漏洞发现与分析（VULNERABILITY ANALYSIS）

**目标**：把攻击面转化为一份「可验证、可利用、有优先级」的漏洞队列。进入条件：测试计划已批准。

## 分步动作

1. **S4-1 已知漏洞三通道（必做，全部执行）**：① nuclei 批量验证（按指纹选模板组，限速）；② searchsploit/NVD 按版本逐组件检索人工核对（load_skill cve-weaponization）；③ 指驱动的组件专项剧本（load_skill：java-deser-playbook / spring-family / middleware-web / cms-playbook / weak-cred-bruteforce）。三通道结果合并去重后进入 S4-7。
2. **S4-2 手工漏洞发现（必做，扫描器盲区）**：先 load_skill 按类载入手册。本头只列目录，**完整检查项以技能库为准，禁止只测本头列举的样例**（路由见 00-router）：注入类（sqli-deep/cmdi-deep/ssti-engine-map/xxe-full）、客户端类（xss-context/logic-csrf-deser/prototype-pollution）、服务端类（ssrf-deep/upload-bypass/path-traversal）、协议类（request-smuggling/cache-poisoning）、接口类（graphql-websocket）、认证类（auth-flow-deep/jwt-crypto/auth-bypass）、逻辑与越权（logic-csrf-deser/api-idor）、0day 工作流（hypothesis-0day）、凑链工作流（capability-primitive-search：零散低危 → 能力原语标注 → RCE 六等式凑链，扫不出单点高危时的强制收口动作）。差异测试（基线 vs 变异）为通用方法。**预算按广度优先轮转执行（loop-core 深度测试纪律 7/8）：先每类最小探针、全类有结论再深化**；无自述面清单的目标执行「陌生环境五轨深挖」（纪律 9）；对自述面/已知 CVE 映射之外的发现 record_finding 时标注 `【清单外】`（潜在 0day 面）。
3. **S4-3 代码审计（白盒，如提供源码）**：审计注入、越权、逻辑缺陷、硬编码密钥、危险反序列化；关键发现人工复核。无源码则跳过并说明。**认证前置类测试项（登录后注入/越权/存储型）在 S4 即可走 session-state-chain 建会话先行验证**，不留到 S5 才发现缺登录态。
4. **S4-4 配置与架构审查**：云 IAM、容器配置、TLS、鉴权链路；AI 组件重点：RAG 权限过滤、Agent 工具权限、输出处理链。
5. **S4-5 AI 专项风险分析**：对齐 LLM01-10（2026 版，编号映射与 2025 交叉表见 heads/specA.md）逐项排查：提示注入面、敏感信息泄露、过度代理、供应链、数据与模型投毒、无限制资源消耗、误导信息、隐藏上下文暴露、向量与嵌入、输出处理不当。
5a. **S4-5a 并行扇出（可选）**：当存在 ≥3 个相互独立的测试单元（如多个注入点分别验证、多个组件指纹分别检索）时，spawn_subagent 并行派发（objective 写清「目标×漏洞类×判据」），主头继续自己的队列并定期 poll_subagents 整合——单元结果已实时入覆盖矩阵与黑板，主头只做去重与链化。
6. **S4-6 结果去噪与组合分析**：对扫描结果聚类去噪；推理组合漏洞链（如 SSRF + 云元数据接口 → 临时凭据）。**每条入库发现按 capability-primitive-search 标注能力原语（primitive:READ/WRITE/EXEC/SSRF/SQLI/AUTHZ/CRED…）**；只有零散低危时必做原语凑链搜索（正向扩展/反向回推），把缺口列为下一轮测试计划。
7. **S4-7 验证与置信度评级**：每条漏洞登记：位置/描述/复现思路/置信度（确证·疑似·待查），形成待利用队列。**待利用队列每项标注 `access: anonymous | pre-auth | post-auth` 与 `impact-rank`（RCE 系=1 > 认证绕过/接管=2 > SQLi 可提数=3 > SSRF 可达云元数据/内网=4 > 上传落点可控=5 > 其余），S5 按 impact-rank 升序消费**。高危项定级「确证」前 load_skill evidence-standard 对照该类判据（detail 引用判据项）。认证类队列项受阻于前端加密协议/验证码/UA 指纹时，标注「browser-auth 路线」移交 S5-2a，不作为测试不能执行的结论。**无凭证项目 S4 收口摘要必须报告三行：匿名确证高危数 / 身份获取路线尝试记录（identity-bootstrapping L1-L6 逐条结论）/ 认证后项的处置状态——缺一不可。**
8. **S4-8 自述面清单对账（工作区存在 checklist.json 时必做）**：read_file 读 `checklist.json`，逐条测试并在每次 update_coverage 时于 Endpoint/Notes **引用条目文本或 C 编号**（引擎 G2 门按此归账）；本轮无法测试的条目用 write_file 更新 checklist.json 标注 `"status":"deferred"`/`"excluded"` 并附 reason——两者缺一的条目会在收口时被引擎硬门拦截。延期/排除超过清单一半时先做一轮广度探针再收口。
9. **S4-9 多目标分段收口（引擎对账门，批次6）**：多目标项目收口时引擎对账目标覆盖——**每个目标必须「已 update_coverage」（Endpoint/Notes 含目标）或「已列入待续清单/档案目标」**；引擎观测到 ≥2 个目标已真实覆盖而仍有目标两处皆无时拦截收口。**分组产出约定**：按目标组推进时每组结论写 `deliverables/s4-<目标或组名>.md`（含该组漏洞清单与待续项），S8 报告承接合并；收口前逐组核对 update_coverage 已登记。
10. **S4-10 威胁清单实测回填（v4.8 R6，贯穿本阶段每轮）**：协议还原/参数语义判定/新端点结构等实测事实，凡**推翻或新增** s3 威胁清单条目 → **当轮回填**（禁止攒到收口）：①`extends TH-xx`——新事实挂原条目「实测进展」小节，不新增条目；②`replaces TH-xx`——实测推翻 → 原条目转 deprecated 留痕；③`creates`——全新面 → 新编号（清单外口径计分）。**回填前先 search_memory 对照原清单**；与 B1 判重同源（同组件×同威胁类×同机制 → 合并）。s3《筛查矩阵判定表》的 `待判定` 行（双假设并列）在本阶段实测裁决后同步收敛：判定表追加裁决行注记（保留原待判定行留痕），威胁清单同步 extends/replaces。回填记录写入本阶段交付物《威胁清单回填记录》小节（三态关系逐条留痕）。

## v4.6 W3 增补（Authz-Diff 标准动作）

- 端点表就绪后执行鉴权差分矩阵（load_skill authz-diff；无 WAF 目标直连 `python3 /opt/tools/authz-diff.py --base … --endpoints evidence/s3-api-endpoints.txt --control <已知anon端点>`）——审计实证：全部未授权类高危都是该矩阵的手工版产物，引擎化后 128 端点级是必做项而非 7/124；
- **v5.1 全量覆盖率硬门**：矩阵按 authz-diff 第五节执行——无 token 列纯匿名全量跑（**禁止推迟到身份后**），端点表 N 行 100% 入矩阵、三态处置、Notes 记账 `diffed/total`；**收口摘要必须分别报告**端点登记率**（diffed/total=100% 为归账门槛）与**实际测试执行率**（tested/blocked/deferred 分列），缺口行无三态处置不得 complete_stage**（离线门 coverage_gate 端点表↔矩阵对账拦截）；
- 签名/加密协议还原按 load_skill crypto-offensive：oracle 落盘即入投递队列（破解≠终点）。

## v4.7 增补（C1 验证码 OCR 产品化）

- 验证码攻坚线（identity-bootstrapping L4）默认工具：`python3 /opt/tools/captcha-ocr.py --image <PBM>`（列投影分割+去噪+位移对齐模板匹配）；PBM 可由验证码图片二值化转换（evidence-standard 判据：识别后必须「取码→识别→立即提交」单会话闭环，跨会话复用=假阴性）。分割数与期望不符（粘连/断裂）时返回 None——降级人工读码/browser-auth，不要硬套。

## v4.8 W4/W6 增补（身份获取编排 + 注入与业务逻辑自动化）

- **W4 六轨编排（引擎编排层）**：无凭证且有登录面时按上下文包「身份获取编排」提示逐轨推进（L1→L6），每轨 record_vt（title 前缀 [W4-L1]..[W4-L6]，不适用轨也登记注明「无对应面」）；首轨命中即 session-state-chain 建会话；收口门硬校验逐轨留痕（全轨失败时移交链完整）。
- **W6 注入通道标准件**：挑战型 WAF 下 sqlmap/nuclei 经 chain-proxy 上游代理链带挑战态运行（`python3 /opt/tools/chain-proxy.py --from-snapshot <快照> --emit|--serve`）；盲注三通道自动裁决 blind-inject-adjudicator.py（布尔/时延/带外建议，先三通道裁决再人工深化）。
- **W6 业务逻辑标准件**：IDOR 自动基线 idor-baseline.py（采样→自增判定→匿名差分→量化，C-08）；状态机不变量 logic-invariant.py（跳步/逆序/重复提交违例探测，默认 dry-run，--live 需 ROE write_policy 允许，C-19/C-20）。

## v5.4 S4 增补（架构信号保底 + 带态矩阵第二遍 + 密钥/SSO 强制链）

- **架构信号 VT 保底**：S2-10 登记的 P0 架构信号 VT 在 S4-7 排序与预算收口时**优先于泛化收口消费**；因预算被挤出的必须进 ready_but_unexecuted 由 S5 承接（承接反蒸发硬规则）。
- **执行卡驱动（v5.8.0）**：s3《筛查矩阵判定表》中每条带执行卡的假设 = s4 直接投递单元——按入口/首探针/阴阳信号/停止阈值执行并 update_coverage；执行卡缺失的类按技能矩阵补卡后再测。
- **带态越权矩阵（标准化第二遍，必做）**：authz-diff（匿名面）完成后，凡获得任一登录态（browser-auth / 用户主动提供并入库 / 已确证伪造会话），必须跑第二遍带态矩阵——load_skill api-idor + idor-baseline.py 三轴（用户标识轴 uid/account、资源 ID 轴、功能上下文轴），横向+纵向逐轴三态登记；**禁止只测匿名面就收口**（匿名全库可达 ≠ 带态越权已测）。
- **密钥/SSO 强制链**：密钥材料泄露（预览/部分密钥/口令类）→ load_skill jwt-crypto 全算法族裁决（alg 置换/算法混淆/kid 路径类/jku-jwk 注入/密钥派生可行性），禁止只试离线爆破；SSO/票据/扫码机制确证 → 滥用矩阵逐项过（重放/固定/跨用户消费/QR 参数操纵），结论三态登记。
## v6.0.1 S4 增补（类级处置硬门 C27 + 批量隔离通道）

- **C27 类级处置（引擎门，v6.0.1）**：s3《筛查矩阵判定表》每个「假设/待判定」类在 S4/S5 收口时必须三选一留痕——①update_coverage 引用 C 编号（Endpoint/Notes）②record_vt（title/启动条件含 C 编号）③写 `deliverables/s6-27类收口对账表.md` 该行为「已测/合规豁免（no_credentials|production_safe_write_prohibited|environment_unreachable + 依据）/环境不可达」+ 证据指针。**引擎 C27 门机械对账，未处置类直接拦截收口**——"执行卡投递"从提示词约定升级为引擎强制（实证：某任务 18 假设类 6 类静默跳过且交付层不可见）。
- **run_batch 批量隔离通道（引擎，v6.0.1 P2）**：多主机 nuclei/httpx/ffuf 类批量扫描一律用 run_batch（command 含 {{TARGET}} 占位符 + targets 换行清单）——逐目标独立进程组/超时/日志，单目标挂起不拖死整批（实证：nuclei 单进程批量一个 403 慢响应主机致整批 >5min 零产出、已知漏洞通道失效）。模板与逐目标实例风险一致性由引擎校验；killed/零产出必须 record_vt（title 含 job id），C31 门收口机械对账。
- **候选账本（引擎 C28）**：任何「待评估/未定性」线索立即 record_candidate 登记；收口前 update_candidate 三选一归位（finding/vt/excluded）——禁止「待评估」悬空进报告（实证：GetCaptchaImg 案三不管）。
