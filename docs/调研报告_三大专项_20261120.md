# 九头鸟三大专项方法论调研与差距分析

**调研基准日：2026-11-20**  
**范围：** AI（LLM/Agent）、移动 APP、小程序专项头；公开标准、平台文档、工具发布记录、公开研究。  
**目标环境假设：** 仅限书面授权目标、确认过的 ROE、测试租户/账号及可控数据。本文是方法论建议，不含可直接复制的攻击载荷，也不构成对平台基础设施的测试授权。

## 摘要

现有 A1-A11、S1-S5/D1-D6、W1-W6 已覆盖传统 LLM 应用、移动应用及小程序的主要测试链，授权边界和低影响验证要求也较完整。主要差距集中在版本基线和新型信任边界，而非基础测试流程缺失：

- **AI：** OWASP 已从 2025 LLM Top 10 演进到 2026 清单，并新增独立的 Agentic Applications Top 10 与 Agent Control Standard；2026 年底还发布了 Agent 安全及 GenAI 数据安全的新版实施指南。MITRE ATLAS 数据集在 2026 年持续加入 MCP、Agent 工具、记忆、服务路由和多模态相关技术。当前 A 头需要重做映射，并补齐 MCP/A2A 委托链、Agent 持久化上下文和 LLM 网关路径。[R01-R07][R50]
- **APP：** MASVS 2.1 新增隐私控制组，MASTG 2.0 于 2026 年形成新的机器可读测试结构；旧版 checklist 引用方式已经过时。Android Play Integrity、Apple App Attest 与 Apple 隐私清单使静态/动态测试都需要观察服务端对完整性信号的实际决策。Android 开发者身份验证于 2026-09 在部分地区开始生效；Android SDK Sandbox 及其兼容库状态也需按目标系统版本核验。[R24-R34][R48-R49]
- **小程序：** W1-W6 的解包、客户端、接口、云函数主链仍有效，但 wxappUnpacker 不应再作为唯一工具；平台登录/身份绑定、宿主 API 与跨小程序隔离、云端服务身份和权限边界还没有独立测试项。公开研究已在登录授权、云开发配置和平台权限 API 上观察到规模化问题。[R39-R47]
- **治理与授权：** 中国 APP/SDK 专项治理、工信部 APP 备案要求和抖音小程序平台规则影响报告口径及 ROE 范围。平台机制或平台基础设施不应仅凭目标应用授权进行测试；应在报告中把合规发现与可利用的技术漏洞分开描述。[R35-R38]

建议先更新三套专项头采用的标准、工具和攻击技术映射（P0），再增加 Agent 协议/网关、移动端完整性/隐私和小程序身份/云权限条目（P1），最后通过有版本号的案例库和证据模板保持月度或季度更新（P2）。

## 一、专项 A：AI（LLM/Agent）目标渗透测试

### 1.2 调研发现

**OWASP 清单已更新，Agent 风险单列。** OWASP GenAI Security Project 的 LLM Top 10 已发布 2026 版，当前次序为 LLM01 Prompt Injection、02 Sensitive Information Disclosure、03 Excessive Agency、04 Supply Chain、05 Data and Model Poisoning、06 Unbounded Consumption、07 Misinformation、08 Hidden Context Exposure、09 Vector and Embedding Weaknesses、10 Improper Output Handling。相较 2025 版，提示注入进一步包含多模态和间接路径；系统提示泄漏扩展为 Hidden Context Exposure；Excessive Agency 上移到第 3、Unbounded Consumption 上移 4 位、Improper Output Handling 调整到第 10。应以 2026 分类做当前映射，同时保留旧编号交叉表，避免历史报告失去可比性。项目页称其基于事件及从业者判断形成，不应把名次当成单个目标的风险排序。[R01-R02]

本报告将 OWASP 正式发布的 LLM Top 10 和 Agentic Applications Top 10 作为 AI 应用测试的当前分类基线；未发现与其并列、持续维护的独立 OWASP “NLP Top 10”应用测试清单。自然语言处理模型的相关风险按适用场景映射到上述清单，不将 NLP 与 LLM 风险分类视为同一版本体系。[R01-R03]

OWASP Top 10 for Agentic Applications 2026 将 Agent Goal Hijack、Tool Misuse、Identity and Privilege Abuse、Supply Chain、Unexpected Code Execution、Memory & Context Poisoning、Insecure Inter-Agent Communication、Cascading Failures、Human-Agent Trust Exploitation、Rogue Agents 独立列项。它补足了传统“模型输入/输出”分类难以表达的授权委托、持久状态、Agent 间消息及级联故障问题。OWASP Agent Control Standard 则偏运行时可观察、可审计和可执行控制，可作为防御验证参照，不替代渗透测试分类。[R02-R04]

**ATLAS 是滚动数据集，旧编号需校验。** 截至调研基准日，MITRE ATLAS 数据仓库显示内容版本 2026.10、格式版本 6.1.0。近期新增/扩展的 AML 技术包括 T0135 模型输出、T0136 经 AI 界面外传、T0137 训练数据信息、T0140 AI 服务请求路由、T0141 AI 服务 Web 界面元数据清理、T0142 事件触发执行、T0143 LLM 提示传播、T0144 恢复模型内部信息、T0145 投毒 Agent 学习环境；T0085 下也有 Agent 工具、对话上下文与记忆、系统指令等细分项。2026 年更新还记录了 MCP/Agent 工具投毒和资源消耗案例。部分现有 A 头编号已迁移或更细分，例如旧系统指令/对话上下文条目被拆为 Agent 工具、上下文记忆、系统指令子技术。应从固定版本数据生成映射表，逐一校验当前 A 头里 T0056/T0057/T0082/T0108 等引用，不能仅沿用旧网页编号。[R05-R07]

**MCP 与 A2A 把信任边界从模型扩展到协议与身份。** MCP 在 2026-07-28 规范更新中调整为无状态请求、每请求携带版本等机制，并继续演进授权和任务能力；测试需记录服务端与客户端实际实现的规范版本。其公开安全考虑和 OWASP MCP 指南强调 OAuth 受众绑定、令牌不透传、混淆代理、工具描述/实现被替换、过宽权限、SSRF、工具结果诱导和出站数据流。A2A 用于 Agent 发现、能力协商与任务/上下文交换；公开研究报告了跨轮上下文、身份传递和能力声明等风险，厂商研究中的 Session Smuggling 属于协议使用模式风险分析，并未声称 A2A 标准本身存在缺陷。授权测试应只在专用 Agent/工具租户中确认身份、消息来源、上下文和委托边界。[R08-R13]

**网关和防护产品需做端到端验证。** AWS Bedrock Guardrails、Azure Prompt Shields、Lakera 和 Prisma AIRS 等公开产品资料显示，检测点可能分别位于用户输入、文档/检索内容、模型响应或工具策略层，覆盖范围并不一致。例如 AWS 文档明确指出其 prompt attack 检测不会分析工具结果或工具定义；Azure 文档说明文档攻击检测需启用相应选项。公开自适应攻击研究表明，静态过滤器和基于分类器的防护在攻击者针对防护本身调整时可能退化；研究结果依赖特定模型、基准和设定，不能直接外推为任何产品的实测结论。测试要核对每层的输入覆盖、放行/阻断决策、策略绕过后的最小权限和遥测证据。[R17-R21]

**权威框架支持“受控、可重复、贴近部署”的红队方法。** NIST AI RMF 与 GenAI Profile 不是漏洞清单；其 MEASURE 2.5 强调有效性、可靠性与外推限制，MEASURE 2.10 明确将红队用于隐私风险评估，MANAGE 1.3 提出监控风险控制有效性。NIST 2026 ARIA Evaluation Planning Manual 将模型测试、红队和用户测试结合，适合作为测试计划与证据的组织框架。ISO/IEC 42001:2023 是 AI 管理体系要求，不是技术测试目录；可用于确定治理、责任、评审和持续改进证据，但不应在没有标准全文和适用性判断时声称某个漏洞违反了特定条款。[R14-R16]

**工具建议按能力与版本管理。** PyRIT 适合多轮、转换器和场景化红队评估，garak 适合模型探针与检测器覆盖；二者不能替代面向真实应用的工具链/权限测试。建议按项目锁定版本、配置、模型与探针集，并保存只含必要元数据的运行记录。[R22-R23]

OWASP GenAI 系列还在 2026 年发布 Securing Agentic Applications V2（2026-11-10）和 GenAI Data Security Best Practices V2（2026-11 起分篇发布）。前者把安全架构、身份/访问控制、运行时保护、供应链和保障测试落到单 Agent/多 Agent 场景；后者补充 GenAI 数据分类、治理和生命周期实践。它们是实施指南而非新的风险 Top 10，可用于扩充 A1、A6、A10、A11 的测试问题与证据，不应混用其条目编号。[R50]

### 1.3 缺口清单

- **⚠️ A3-A11：2026 分类与 ATLAS 映射基线。** 将 2025 OWASP 分类更新为 LLM Top 10 2026 与 Agentic Top 10 2026 双映射；固定 ATLAS 数据版本/格式版本，并审计旧编号迁移。保留授权确认、合成数据、模拟工具和低影响预算约束。
- **❌ A12 Agent 协议与委托信任边界：** 对 MCP、A2A 等协议检查身份验证、令牌受众和委托、能力/工具定义变更、上下文来源、消息完整性与出站路径，验证结果限于测试 Agent 和测试工具。
- **❌ A13 Agent 记忆与目标完整性：** 检查短期/长期记忆、检索语料、会话恢复和跨任务共享的写入者、保留期、隔离及删除控制，确认低可信内容不能持久改变后续授权行为。
- **❌ A14 LLM 网关与策略链：** 识别模型代理、内容安全、防火墙、缓存、日志和路由层，分别验证输入/检索/工具结果/输出经过哪些控制及失败时行为，并记录审计与版本证据。

### 2.2 调研发现

**OWASP 测试结构已经重构。** MASVS 2.1.0 增加 MASVS-PRIVACY 控制组，关注敏感数据/资源最小化、用户可识别性、透明度和用户控制。MASTG 2.0.0 于 2026 年成为稳定版，测试内容以机器可读结构和链接关系组织，并与 MASVS、MASWE、测试技术及工具关联；旧 checklist 电子表格不再是可靠的唯一索引。新结构更适合把控制、弱点、测试步骤和证据状态一一关联。[R24-R26]

**工具链应升级并钉住版本。** 截至调研日，官方发布页显示 jadx 1.5.6、Apktool 3.0.3、Frida 17.27.4、objection 1.12.5、MobSF 4.6.4。版本更新带来反编译兼容、资源处理、运行时插桩、iOS/Android 分析和流量观察的变化；这意味着同一测试脚本在不同版本/设备上的结果不能默认等价。MobSF 适合作为静态与动态辅助平台，不应把自动扫描结果直接当作已确认漏洞。[R27-R31]

**平台完整性、开发者身份与隐私沙盒都要按目标环境验证。** Google Play Integrity 将应用/设备相关判定和请求绑定信号提供给应用后端；Apple App Attest 使用设备侧密钥和服务端挑战/断言来支持应用实例验证。测试目标应是：服务端是否校验、信号是否绑定请求、重放/缓存/降级如何处理，以及风险决策是否与业务授权一致。Android 开发者身份验证自 2026-09-30 起已在巴西、印度尼西亚、新加坡和泰国的部分参与应用商店/认证设备开始执行，Google 公布的全球扩展计划从 2027 年开始；这影响应用安装来源和测试包来源证明，应按地区、商店和设备检查，不能笼统视为全球强制策略。Android 平台 SDK Sandbox API 仍是可检查的运行时能力，但官方兼容 Jetpack 库在 2025-12 标记弃用；应先确认目标应用实际采用的平台 API/兼容层和 OS 版本，再评估 SDK 隔离、共享数据与 IPC 边界。Apple Privacy Manifest 和 Required Reason API 影响隐私披露与 API 使用审查；静态声明应与运行时及 SDK 行为比较。[R32-R34][R48-R49]

**中国 APP 专项治理影响隐私测试的证据口径。** 2026 年个人信息保护专项治理聚焦 APP 和 SDK，公开要求涵盖告知与实际收集不一致、未充分取得同意、超范围收集、权限必要性和账号注销/删除等问题。2025 年专项公开范围明确包括 APP、小程序等。工信部 APP 备案要求仍适用于相关应用分发场景。报告应记录版本、授权页面、权限触发时机、实际数据流、SDK 身份与删除路径，并将合规问题和可利用的安全漏洞分栏；不要仅凭隐私告知瑕疵推导技术可利用性。[R35-R38]

### 2.3 缺口清单

- **⚠️ S2-S5、D1-D6：标准和工具版本化。** 将未注明版本的 MASTG/MASVS 更新为 MASVS 2.1.0、MASTG 2.0.0，并引用 MASWE；建立 jadx、Apktool、Frida、objection、MobSF 的已验证版本矩阵、脚本/插件来源和适用设备范围。
- **❌ D7 平台应用完整性与服务端判定：** 评估 Android Play Integrity、Apple App Attest 等信号的挑战绑定、服务端验证、重放/缓存/降级处理及其对高风险业务操作的实际授权影响。
- **❌ D8 隐私清单与 SDK 数据行为：** 对照隐私清单/权限声明/用户告知与运行时数据流，识别第三方 SDK 的采集、共享、保留和退出/删除路径；适用时评估 Android SDK Sandbox 的数据/IPC 边界；以测试数据和经授权设备验证。

### 3.2 调研发现

**解包工具生态分散，格式适配要以样本验证。** wxappUnpacker 停更后，社区 fork、桌面解包工具和 Go 实现仍在迭代；Gwxapkg 等项目提供扫描、解密/还原或静态审计能力，维护 fork 则尝试兼容较新的 Node 运行时及分包结构。公开研究也采用从授权运行环境取包、核对 AppID/元信息和哈希、收集主包及可获取子包的做法。由于未找到平台公开的稳定 wxapkg 格式版本规范，报告中应注明包来源、解密条件、子包覆盖率和解析失败项，不能把“成功解包”描述成完整源码恢复。[R39-R40]

**平台安全与备案规则持续变化，授权需覆盖真实目标边界。** 工信部关于 APP 备案的通知覆盖相应 APP 和小程序分发场景；抖音开发者文档提供小程序备案要求，其运营规范允许对提交代码及后台进行审核/测试，同时禁止利用平台漏洞或绕过平台机制。由此应在 ROE 中区分目标小程序/自有后端、云服务租户，以及微信/支付宝/抖音平台本身；后者的基础设施和其他租户不因目标授权而自动纳入范围。[R36-R38]

**三平台的审核和隐私接口要求需要分别建档。** 微信要求开发者在处理个人信息时配置隐私保护指引，并在用户阅读、同意后调用对应隐私接口；腾讯云 2025 年适配说明还指出，提审代码检测可能漏掉较隐蔽的组件/接口使用，需结合运行表现和审核反馈核验。支付宝平台协议说明其可在发布前审查小程序，并在发布后持续测试/检查；平台文档也要求开发者说明主体、服务类目、必要资质并取得用户信息处理所需授权。抖音规范明确可对提交代码及后台进行审核，同时禁止绕过平台机制或利用平台漏洞。测试方案应据此核验隐私接口调用前的授权状态、提审声明与运行行为，并把平台自身审查/基础设施排除在目标应用授权之外。[R37-R38][R51-R52]

**云开发的“规则”边界因平台和调用身份而异。** 腾讯云开发文档指出客户端数据库安全规则限制客户端访问，云函数或服务端请求可处于不同的信任/权限路径；抖音云开发文档也区分客户端数据库访问控制与服务端/控制面能力，并提供函数、HTTP 触发、环境变量和 IAM 能力。支付宝小程序安全指引强调前端不可信、密钥不得放在客户端、服务端应完成认证与限流；具体云产品/托管方案可能不同，须先识别实际后端，不应套用单一云平台假设。测试时要分别核对客户端 SDK、函数调用者、HTTP 入口、服务身份、数据规则和部署环境。[R41-R43]

**公开研究显示登录、云安全和宿主能力均是独立攻击面。** 2026 年 MiniAuth 研究分析小程序 OAuth/登录链路，报告了凭证暴露、身份伪造和认证绕过类误用；复旦团队的 ICREMiner 研究报告在大规模云开发小程序中发现多项服务端/云端高风险操作；其他公开工作研究了跨小程序 Cookie 共享及平台权限 API 检查不足。它们是研究数据和方法的证据，不应直接当作九头鸟所测平台或目标存在同一缺陷的证明。[R44-R47]

**监管发现和安全漏洞应分别定性。** 小程序备案、隐私告知、平台审核政策和 SDK 处理问题可能构成治理/合规发现；只有当测试确认了未授权数据访问、身份混淆、跨租户影响或其他技术安全影响时，才按漏洞路径和影响定级。工信部和网信部门公开专项治理内容可支持报告的治理背景，但不能替代法律适用性意见。[R35-R38]

### 3.3 缺口清单

- **⚠️ W1：解包与覆盖完整性。** 维护经审查的工具候选清单（如活跃 fork、Gwxapkg 等），固定工具来源与哈希；在报告记录主包/分包、加密状态、还原率及不可见内容，避免以工具输出替代原始包证据。
- **⚠️ W2/W4：平台登录和密钥边界。** 区分公开标识与秘密凭据，增加 OAuth/平台登录授权码兑换、用户身份绑定、会话轮换/撤销和服务端验证；对真实手机号、支付和用户数据仍使用测试数据。
- **⚠️ W5：云端调用身份与权限模型。** 分别画出客户端、云函数、HTTP 触发器、服务端 SDK、管理面和存储的权限路径；验证最小权限、测试/生产隔离及服务端所有权检查。
- **❌ W7 平台登录态与身份绑定：** 测试登录授权码生命周期、服务端换取会话、用户身份与资源所有权映射、令牌刷新/撤销及防重放，不访问真实用户账号。
- **❌ W8 宿主能力与跨小程序隔离：** 评估宿主桥接、敏感权限 API、WebView/页面来源、Cookie/会话共享及跨小程序数据边界，确认平台 API 的授权检查和错误处理。
- **❌ W9 云资源身份与部署边界：** 盘点云函数调用来源、HTTP 暴露、服务身份/IAM、数据库规则、对象存储及开发/生产配置差异，使用无敏感数据的受控对象证明访问控制结论。
- **❌ W10 备案、隐私披露与 SDK 治理证据：** 将备案主体/标识、权限说明、隐私政策、SDK 收集与数据删除路径作为独立治理检查项，并与技术漏洞分开定性。

## 四、跨专项共性发现

1. **身份和委托链是共同边界。** AI Agent 的工具/Agent 委托、APP 的客户端到 API 会话、小程序的宿主登录到云函数服务身份，都需要明确“谁代表谁调用什么资源”。仅验证客户端可控不够，还要验证服务端的主体、租户与资源所有权判断。
2. **版本就是测试条件的一部分。** OWASP、ATLAS、移动工具、MCP 规范和小程序解包实现都处于迭代中。报告至少记录标准版本/数据日期、工具版本、目标平台版本、模型/网关或云环境版本及配置快照；历史映射保留，避免静默覆盖。
3. **从内容检测转向行为结果。** AI 测试需要确认低可信上下文是否改变了工具调用、身份或数据边界；移动端与小程序测试则确认客户端行为是否被服务端授权。结果要有可验证的安全影响，避免将过滤命中、代码字符串或客户端绕过单独认定为漏洞。
4. **隐私与最小证据同步纳入流程。** 使用合成标记、测试账号和授权数据；仅保留证明结论所需的请求/响应片段、配置差异和哈希。发现隐私/备案问题时单独标注依据、技术影响与适用范围。
5. **治理标准提供计划和证据框架，不自动等同漏洞分类。** NIST AI RMF/GenAI Profile、ISO/IEC 42001 及国内治理要求可用于设定责任、风险评估和持续改进证据；技术发现仍应根据可复现的攻击路径、控制失效和影响定级。

## 五、优先级建议

### P0：更新版本基线与现有映射

- 将 A 头映射到 OWASP LLM Top 10 2026、OWASP Agentic Top 10 2026 和 MITRE ATLAS 2026.10；复核旧 ATLAS 编号并保存迁移表。
- 将 B1 标准基线更新为 MASVS 2.1、MASTG 2.0 和 MASWE；废止对旧版 checklist 单一依赖，锁定本地工具版本和可复现环境。
- 更新 B2 的解包工具来源、版本和包完整性记录；为 APP/小程序统一增加版本、身份、环境和授权范围清单。
- 在 AI、APP、小程序报告模板中固定授权租户、测试数据、低影响预算、禁止范围、数据留存和复测证据字段。

### P1：补上明确的新测试链

- 新增 A12-A14：Agent 协议委托、记忆/上下文持久化、LLM 网关与策略链。
- 新增 D7-D8：平台完整性信号的服务端决策，以及隐私清单/SDK 运行行为。
- 新增 W7-W10：平台登录身份绑定、宿主能力/跨小程序隔离、云资源身份/部署边界、备案与隐私治理证据。
- 将 MCP/A2A、App Attest/Play Integrity 与云开发检查先限定在测试账号、隔离租户和受控对象，形成正反向授权证据。

### P2：建立持续维护机制

- 维护季度更新清单：OWASP/ATLAS 版本、工具发布、平台规则/备案变化、公开研究和已验证测试案例。
- 将标准控制、弱点类别、测试步骤、工具及证据状态做可追溯关联；记录测试覆盖、未覆盖原因和适用限制。
- 为网关、防护与 Agent 工具链增加版本化基准场景；仅在经授权的测试环境评估拦截、审计、告警和失败关闭行为。
